# Frontend Task Plan

This plan covers the frontend track of [PLAN.md](PLAN.md): every screen the MVP needs, wired to the API contract so the backend can plug in as each router lands. The backend is being built in parallel in a separate branch, so the frontend codes against the contract in PLAN.md and runs on an in-browser mock of that contract until the real endpoints exist. Visual polish comes after the wiring, in a later phase.

## How the work runs

- **Contract first.** Every screen calls the routes in PLAN.md's API contract through `src/lib/api.ts`. Where the contract leaves a detail open, the frontend uses the assumption in the next section; the backend confirms or corrects it.
- **Mock mode.** `npm run dev:mock` serves every route from an in-memory mock backend in `src/mocks/`, seeded with the road-accident case. `npm run dev` talks to FastAPI on port 8000 through the Vite proxy. Screens don't know which one they are using.
- **One branch per task**, named as in PLAN.md (`m<N>/frontend-<topic>`). Frontend branches touch only `frontend/` and `docs/`. They never touch `backend/`, `assets/`, or the 3D feature folders (`features/crime-scene`, `anatomy`, `geographic-area`, `building-viewer`), except T1, which moves the draft files into place.
- **Merge order.** T1 merges to `main` first, because every other branch starts from it. Until a branch is merged, the next task branches from it, so pull requests merge in task order.
- **Wiring before polish.** New screens reuse the draft's existing Tailwind styling. Restyling, shadcn/ui and responsive layout wait for the UI phase at the end.

A task is done when:

- It works end to end in `npm run dev:mock`, and against the real backend once the matching router is on `main`.
- `npm run lint` and `npm run build` pass.
- Every query has a loading, error and empty state, and the screens show no hard-coded case data or invented numbers.
- It has been checked in a headless browser, with screenshots shared in the session.

## Contract assumptions

PLAN.md doesn't pin these down. The frontend builds against the defaults below; the backend session should confirm or correct each one, and the generated `api-types.ts` replaces the hand-written types once the backend is up. The exact request and response shapes are in `frontend/src/types/api.ts`, and `frontend/src/mocks/` implements them.

| Topic | Frontend assumes |
| --- | --- |
| JSON naming | snake_case, as Pydantic emits by default, matching PLAN.md's field names |
| IDs | Integer `id` on every table; `case_number` is a display string generated by the backend, such as `FX-2026-0001` |
| Errors | FastAPI's `{ "detail": ... }`, a string or a validation list |
| Case status | `open`, `in_progress`, `under_review`, `closed` |
| Priority | `critical`, `high`, `medium`, `low` |
| Incident type | `road_accident`, `homicide`, `assault`, `burglary`, `fire`, `other` |
| Evidence type | `document`, `statement`, `photo`, `video`, `audio`, `medical`, `other`; the backend guesses it from the MIME type and the investigator can change it |
| Processing status | `queued`, `processing`, `done`, `failed` |
| Event category | `collision`, `movement`, `witness`, `emergency`, `medical`, `investigation`, `other` |
| Event time precision | `exact`, `minute`, `approximate`, `day` |
| Relationship kind | `drove`, `owns`, `involved_in`, `witnessed`, `located_at`, `mentions`, `supports`, `contradicts`, `other`; `label` stays free text |
| Report templates | `court`, `summary`, `custody`, `medical` |
| Alert severity | `info`, `warning`, `critical` |
| Case location | `cases` has no location column. The create modal posts an `incident_site` row to `/locations` with an address and optional lat/lng |
| Workspace call | `GET /cases/{id}/workspace` also returns `locations`, plus computed `counts` (evidence, pending reviews, open conflicts, reviewed and total AI items) |
| Evidence upload | Multipart field `files`, several files per request; the response is the list of created evidence rows |
| Processing updates | Polling: the evidence list refetches every 3 seconds while any item is `queued` or `processing` |
| File access | `<img>`, `<video>`, `<audio>` and `<iframe>` can't send headers, so `GET /evidence/{id}/file` takes `?investigator_id=` for the audit entry and `?download=1` to log "exported" instead of "viewed" |
| Graph | `GET /cases/{id}/graph` returns nodes `{ id: "person:3", type, record_id, label, sublabel, review_status }` and edges `{ id, relationship_id, source, target, kind, label, confidence, flagged, review_status }`, without positions; the frontend lays them out |
| Ask | Request `{ question, history: [{ role, content }] }`; response `{ answer, citations: [{ chunk_id, evidence_id, evidence_title, page, passage }], follow_ups: [] }`. The conversation is kept in the browser, not stored by the backend |
| Timestamps | Cases carry `created_at` and `updated_at`; evidence carries `created_at` (upload time, separate from `collected_at`) |
| Deletes | Deleting a person, object or location also deletes the relationships that point at it |
| Report history | Needs a new route, `GET /cases/{id}/reports`, to list a case's stored reports |
| Event and injury titles | Neither table has a title. The timeline shows the first line of `description`; injury markers are placed from `body_region` |

## Phase 1: Foundation

### T1 Scaffold (`m1/frontend-scaffold`)

Moves the draft into the repo and sets up the skeleton from PLAN.md. Every screen still renders the draft's mock case, so `main` keeps starting.

- Split `CaseWorkspace.tsx` into one file per module under `features/`, so later tasks don't all edit the same file. Drop the CCTV, Phone Records and GPS modules, which PLAN.md removes.

- Copy `ai-forensic-investigation-suite/` from the varaxis repo into `frontend/`, and place files as in PLAN.md's "Where each draft file goes" table.
- Delete `IndividualCaseView.tsx`, `Sidebar.tsx`, `metadata.json`, the draft's `README.md`, `.env.example` and `bun.lock`. Rename the package to `forensix-frontend`, set the page title to Forensix, and drop "AI FORUM v5.0".
- Packages: add `react-router-dom`, `@tanstack/react-query`, `zustand`, and `openapi-typescript` as a dev dependency. Remove `express`, `@types/express`, `dotenv`, `tsx`, `@google/genai` and the unused `motion`. Use npm, with one lockfile.
- Config: point `@` at `src/` in `tsconfig.json` and `vite.config.ts`; proxy `/api` to `http://localhost:8000`; set `envDir: '..'` and `publicDir: '../assets'`. Scripts: `dev`, `dev:mock` (`vite --mode mock`), `build`, `lint`, `gen:api`.
- Routing in `main.tsx` with a `QueryClientProvider`: `/` dashboard, `/cases`, `/cases/:caseId/:module?`, `/evidence`, `/reports`, and a not-found page. The URL replaces `App.tsx`'s view, case and module state.
- Add `frontend/.gitignore`. Root files (`README.md`, `.gitignore`, `.env.example`) are left to the backend setup to avoid conflicts.

Done when the app runs on port 3000 with the same screens, and the back button and a refresh keep the current case and module.

### T2 API layer and mock backend (`m1/frontend-api-layer`)

Adds everything the feature tasks build on. No screen changes yet.

- `src/types/api.ts`: request and response types written by hand from PLAN.md's data model and the assumptions above.
- `src/lib/api.ts`: fetch wrapper with the `/api` base, JSON and multipart bodies, the `X-Investigator-Id` header from the investigator store, an `ApiError` built from FastAPI's `detail`, and `fileUrl(evidenceId, { download })`.
- `src/mocks/`: an in-memory implementation of every MVP route, active only when `import.meta.env.MODE === 'mock'`. It computes real SHA-256 hashes of uploads with Web Crypto, moves new evidence from `queued` to `done` after a few seconds, writes audit entries, and keeps uploaded files as object URLs. Mock data resets on reload.
- `src/hooks/`: one TanStack Query file per router (cases, evidence, people, search, review, graph, timeline, reconstruction, reports, dashboard), with shared query keys and invalidation after each mutation.
- `src/stores/`: the current investigator (kept in localStorage), the selected record and open evidence, and the active reconstruction and stage.
- `src/lib/format.ts`: dates, time ranges with their precision, file sizes.
- `src/components/shared/`: loading, error and empty states; status, priority, review and processing badges; an initials avatar, since persons and investigators have no photo; a citation chip.

The mock seed is the MVP case: a car and a delivery van collide at a signal-controlled junction at about 21:40. It holds both drivers (one injured), two witnesses, the two vehicles and a phone, the junction and the witness and vehicle positions, and a police report, two witness statements that disagree on the signal colour, scene photos, a CCTV clip, an emergency call and a medical report. Some AI proposals are still pending review, and one conflict about the signal colour is open. It also has two reconstruction scenarios ("van ran the red", "car ran the red"), each with Approach and Impact stages. Seed files are small generated text and SVG files, so previews work without the backend. The backend's `seed.py` should load the same case, so screens look the same when mocks are switched off.

Done when every hook returns seed data in mock mode.

## Phase 2: Core features (M1)

Screens that aren't wired yet show a "not wired yet" placeholder inside the workspace instead of the draft's homicide data. `data/mockData.ts` is deleted once its last user is gone.

### T3 Cases, header and case creation (`m1/frontend-cases`)

Routes: `GET /investigators`, `GET /cases?q=&status=&priority=`, `POST /cases`, then `POST /cases/{id}/locations`, `/persons`, `/objects` and `/evidence`.

- Header: an investigator picker that sets `X-Investigator-Id`, and a global search dropdown that calls `GET /cases?q=` as the user types and opens the chosen case.
- Cases directory: filters sent to the server; columns for case number, title, incident type, status, priority, lead, created date and evidence count.
- Create case modal, rebuilt to save only what the officer enters:
  1. **Case:** title (validated before moving on), incident type, priority, incident date and time, lead investigator, team, description.
  2. **Location and evidence:** incident address with optional lat/lng, and a real multi-file picker and drop zone that keeps every file.
  3. **People and vehicles:** persons with role (victim, witness, suspect, other), name, age, condition, contact and notes; vehicles with label, plate, make and colour.
- Fixes the draft bug where the second "Next Step" click submits the form and skips step 3.
- On submit the modal creates the case, then its location, persons, vehicles and uploads, showing progress for each. If a later step fails, the case is kept and the modal says what didn't save. It then opens the new workspace.

Done when a case created in mock mode appears in the directory and opens a workspace showing exactly what was entered.

### T4 Case workspace (`m1/frontend-workspace`)

Routes: `GET /cases/{id}/workspace`, `PATCH /cases/{id}`, `GET`/`POST /cases/{id}/persons|objects|locations`, `PATCH`/`DELETE /persons|objects|locations/{id}`.

- Sidebar modules: Overview, Evidence, People & Vehicles, Review, Canvas, Timeline, Reconstruction, AI Copilot, Reports, Settings. Autopsy stays hidden until T13. Badges show real counts.
- Banner: case number, status and priority (saved with `PATCH`), and an edit dialog for title, description, incident type and date, lead and team. The AI confidence score is removed. Progress is reviewed AI items over all AI items, hidden when there are none.
- Overview: counts, persons by role with their condition, vehicles, incident location, and a link into the canvas. All mock strings listed in PLAN.md and the gap review go.
- People & Vehicles: persons, objects and locations with add, edit and delete. Rows the AI proposed show a pending badge with Confirm and Reject.

Done when the overview shows only data from the workspace call and edits appear everywhere they are used.

### T5 Evidence (`m1/frontend-evidence`)

Routes: `POST`/`GET /cases/{id}/evidence`, `GET /evidence?q=&type=`, `GET`/`PATCH /evidence/{id}`, `GET /evidence/{id}/file`, `POST /evidence/{id}/reprocess`, `POST /cases/{id}/verify`.

- Workspace Evidence tab: drop zone and file picker for several files, upload progress per file, and cards with type, size and processing status that refresh while processing runs.
- Global evidence page: search and type filters sent to the server, a link to each item's case, processing badges. The "100% verified" banner goes.
- Evidence inspector, opened by `?evidence=<id>` in the URL so citations and links can open it:
  - **Preview** by MIME type: PDF in a frame, image, audio and video players, and extracted text for text and Word files.
  - **Text:** extracted text, with the cited passage highlighted.
  - **Details:** SHA-256, size, MIME type, source, collection time, description and notes; type and notes can be edited.
  - **Linked records**, and the **custody ledger** built from audit entries.
  - **Actions:** Download (`?download=1`), and Reprocess for failed or finished items.
- Settings: a Verify integrity button that lists any hash mismatches, replacing the fake "LOCKED" panel.

Done when uploading a PDF, an image and an audio file in mock mode shows a computed SHA-256, a working preview, and a status that moves to done.

## Phase 3: AI intelligence (M2)

### T6 Ask panel and case search (`m2/frontend-ask-panel`)

Routes: `POST /cases/{id}/ask`, `GET /cases/{id}/search?q=`.

- AI Copilot sends the question with the previous turns. It shows the answer; citations as chips naming the evidence and page, each passage beside its source file; and up to three follow-up questions as buttons. Clicking a chip opens the inspector at that passage. It has a waiting state and an error with retry. The greeting with fake counts goes.
- The conversation is kept per case for the browser session.
- Case search: a search box that lists ranked passages with their source; clicking one opens the inspector.

Done when a question asked in mock mode returns a cited answer whose chips open the right passage.

### T7 Review queue (`m2/frontend-review-queue`)

Routes: `GET /cases/{id}/observations?status=`, `PATCH /observations/{id}`, `GET /cases/{id}/conflicts`, `PATCH /conflicts/{id}`.

- A new Review module with Pending, Conflicts and Reviewed tabs. Each observation shows its statement, subject and source passage, with Confirm, Edit and Reject. Each conflict shows its observations side by side, with Mark resolved.
- Pending and open-conflict counts feed the sidebar badge, the overview and case progress. Alerts about reviews open this module.
- The confirm and reject controls become a shared component, reused for AI-proposed persons, vehicles, events and relationships.

Done when confirming or rejecting an item updates the counts and progress straight away.

## Phase 4: Investigation analysis (M3)

### T8 Evidence canvas (`m3/frontend-evidence-canvas`)

Routes: `GET /cases/{id}/graph`, `POST /cases/{id}/relationships`, `PATCH`/`DELETE /relationships/{id}`.

- Replace `NetworkGraphViewer` with React Flow (`@xyflow/react`) in `features/evidence-canvas`, laid out automatically with `@dagrejs/dagre`.
- Node styles for persons by role, vehicles and objects, locations and evidence. Edges show their label; pending edges are dashed and flagged edges red. Filters: flagged only, hide rejected.
- Dragging from one node to another opens a form for kind, label and notes, then saves the link. Selecting an edge offers Confirm, Reject and Delete. Selecting a node opens a panel with the record and its source evidence.
- The overview's graph preview uses the same component in read-only mode.

Done when links added or confirmed on the canvas show immediately and stay after switching tabs.

### T9 Incident timeline (`m3/frontend-timeline`)

Routes: `GET`/`POST /cases/{id}/events?category=`, `PATCH`/`DELETE /events/{id}`, `POST /evidence-links`, `DELETE /evidence-links/{id}`.

- Events sorted by start time. Each shows its time range at its precision ("about 21:40", "21:38 to 21:42"), a certainty badge (established, hypothesis, disputed), location, AI note, review status and source evidence chips.
- Filters by category and certainty.
- An event editor for description, category, start and end, precision, certainty and location, plus linking and unlinking evidence passages. The evidence link picker is shared with T10 and T13.

Done when an event created in the editor appears in order with its linked evidence, and its chips open the inspector.

### T10 Reconstruction stages and scene host (`m3/frontend-reconstruction`)

Routes: `GET`/`POST /cases/{id}/reconstructions`, `GET /reconstructions/{id}`, `POST /reconstructions/{id}/stages`. Hooks for `PUT /stages/{id}/scene-objects` and `GET`/`POST /reconstructions/{id}/annotations` are written here for the 3D track to call.

- Reconstruction module: scenarios with version and assumptions; create a scenario; add a stage with a label, order and events picked from the timeline.
- Stage switcher with previous, next and play. The active stage lives in the stage store, so the timeline highlights that stage's events.
- Compare: two scenarios side by side, stage by stage, with their events.
- Scene host: the panel where the 3D track mounts its viewer from `features/crime-scene`. The viewer reads the reconstruction and active stage from the store and reports the selected scene object; the frontend shows that object's details and linked evidence. Until the viewer lands, a placeholder lists the stage's scene objects so selection can be tested.

Done when switching between two stages changes the highlighted events and listed scene objects, and selecting an object shows its evidence.

## Phase 5: Report, audit and dashboard

### T11 Report and audit trail (`m8/frontend-reports-audit`)

Routes: `POST /cases/{id}/reports`, `GET /reports/{id}`, `GET /cases/{id}/audit`, and the proposed `GET /cases/{id}/reports`.

- One report feature in `features/reports`, used by both the Intelligence Hub (with its case picker) and the workspace Reports tab, replacing the two duplicate drafts.
- Template and options (AI insights, custody ledger) are sent to the backend. The view renders the returned sections: case summary, evidence inventory with hashes, timeline, confirmed findings, open conflicts and uncertainties, reconstruction scenarios with their assumptions, and optionally AI insights and the custody ledger. It shows the report's SHA-256, author and date.
- Export is the browser's print, with a print stylesheet (white page, no app chrome).
- Report history, once the list route exists.
- Audit trail in Settings: actor, action, record, time and before/after detail, filterable by action.
- The fake signatures, the "Victor Vance" paragraph, the fake fingerprint and the `alert()` calls go.

Done when the printed PDF of the seed case contains only data from the report response.

### T12 Dashboard and alerts (`m1/frontend-dashboard`)

Routes: `GET /dashboard`, `GET /alerts`. The backend schedule builds these at hours 11 to 14, so this task comes late even though it belongs to M1.

- Metric cards, status gauge and status bars from the response, including Under Review.
- Incident map: incident lat/lng projected into the existing map panel, with type filters built from the data.
- Alerts feed and header bell; clicking an alert opens the case at the related module.
- Investigators with solved and active counts.
- The fixed numbers (432 cases, "07", 1.2 TB, 84%, 14.2 days, "4 ON DUTY") go.

Done when every number on the dashboard changes when the seed data changes.

## Phase 6: Backend integration

### T14 Switch to the real backend (`m1/frontend-api-integration`)

This repeats at each merge checkpoint in PLAN.md's schedule, rather than happening once at the end.

- As each backend router reaches `main`: run the backend, run `npm run gen:api`, point `src/types/api.ts` at the generated types, fix any mismatch, and run the case flow with mocks off.
- When every MVP route is live: delete `src/mocks/` and the `dev:mock` script.

## Stretch

### T13 Injuries (`m5/frontend-injuries`)

Starts only after the MVP is complete. Routes: `GET`/`POST /cases/{id}/injuries`.

- Keeps the 2D `AnatomicalViewer` until the 3D track's anatomy explorer replaces it. Adds a person selector, places markers from `body_region`, and adds an injury form with evidence links.

## Later: UI enhancement

Once the MVP flow is wired end to end:

- Run `npx shadcn@latest init` and move dialogs, selects, tabs and toasts onto shadcn/ui. This also brings focus trapping, Escape to close, and the animation classes the draft uses but never installed.
- Redesign the screens and replace homicide wording with copy that follows the case's incident type.
- Responsive layout: navigation on small screens, a collapsible workspace sidebar.
- GSAP transitions and camera moves, together with the 3D track.
- Accessibility and keyboard navigation in the canvas and timeline.
- Code-splitting so React Flow and the 3D viewers load only when their tab opens.
